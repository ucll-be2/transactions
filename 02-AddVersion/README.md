# Transactions - Oplossing probleem 2

In de vorige stap hebben we het probleem opgelost dat geld verdwijnt bij een overschrijving naar een niet-bestaande
account door de hele transfer in één transactie te plaatsen. We zullen nu het tweede probleem oplossen: gelijktijdige
bewerkingen op dezelfde account die leiden tot een *lost update*.

Hiervoor kunnen we ***locks*** gebruiken. We willen een bepaalde rij in de database "op slot" zetten om ervoor te
zorgen dat er geen andere bewerkingen op die rij kunnen plaatsvinden totdat de lock wordt vrijgegeven.

Er zijn twee strategieën om dit te doen:

- ***pessimistic locking***: hierbij wordt de rij in de database vergrendeld totdat de transactie is voltooid. Andere bewerkingen die proberen
  dezelfde rij te bewerken, zullen moeten wachten totdat de lock is vrijgegeven.
- ***optimistic locking***: hierbij wordt er **geen** lock geplaatst op de rij in de database. In plaats daarvan
  wordt er een versieveld gebruikt om te controleren of de rij is gewijzigd sinds de laatste keer dat deze is
  opgehaald. Als de rij is gewijzigd, zal de bewerking mislukken en kan de client opnieuw proberen.

We gaan in dit voorbeeld *optimistic locking* gebruiken. Hiervoor voegen we een `@Version` veld toe aan de
[`Account`](src/main/java/be/ucll/be2/transactions/model/Account.java)
entity:

```java
@Entity
public class Account {
    // ...

    @Version
    @Column(nullable = false)
    private Long version;
    
    // ...
}
```

Om het versieveld te demonstreren, voegen we ook een `getVersion()` methode toe aan de `Account` entity:

```java
public Long getVersion() {
    return version;
}
```

Vergeet niet om ook `schema.sql` aan te passen zodat er een `version` kolom wordt toegevoegd aan de `accounts` tabel:

```sql
CREATE TABLE account
(
    id      BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    version BIGINT                                  NOT NULL,
    owner   VARCHAR(255)                            NOT NULL,
    balance DECIMAL                                 NOT NULL,
    CONSTRAINT pk_account PRIMARY KEY (id)
);
```

Bij elke update van een account zal de `version` kolom automatisch worden verhoogd. Als een andere bewerking probeert
dezelfde account te updaten met een verouderde versie, zal er een `OptimisticLockingFailureException` worden gegooid.

Probeer nu opnieuw het scenario van gelijktijdige bewerkingen uit te voeren:

- Maak twee accounts aan:
  ```
  POST /api/v1/accounts {"owner":"Jos Bosmans"} -> id 1, versie 0
  POST /api/v1/accounts {"owner":"Clement Peerens"} -> id 2, versie 0
  ```
- Start 100 euro op account 1:
  ```
  POST /api/v1/accounts/1/deposits {"amount":100}
  ```
  Nu is de versie van account 1 verhoogd naar 1.
- Start een transfer van 50 euro van account 1 naar account 2, maar geef `speed=SLOW` mee:
  ```
  POST /api/v1/transfers {"fromAccountId":1,"toAccountId":2,"amount":50,"speed":"SLOW"}
  ```
- Terwijl de transfer bezig is (er wordt 10 seconden gewacht), doe een opname van 75 euro bij account 1:
  ```
  POST /api/v1/accounts/1/deposits {"amount":75}
  ```
  Nu zal je zien dat er nog maar 25 euro op account 1 staat en dat de versie van account 1 is verhoogd naar 2.
- Wacht tot de transfer klaar is. Je zal zien dat de transfer is mislukt. Het saldo van account 1 is nog steeds 25 euro
  en de versie is 2. De transfer is onderbroken door de `OptimisticLockingFailureException`: dit komt doordat de
  transfer probeert om account 1 te updaten naar versie 2 (omdat die verwacht dat account 1 nog steeds versie 1 heeft),
  maar de versie is al verhoogd naar 2 door de opname. De transfer kan dus niet doorgaan.
- Vraag het saldo van account 1 op:
  ```
  GET /api/v1/accounts/1
  ```
  Je zal zien dat het saldo nog steeds 25 euro is en dat de versie 2 is.

Door een versienummer toe te voegen kunnen we dus eenvoudige conflicten detecteren en voorkomen dat gelijktijdige
bewerkingen leiden tot een *lost update*. In een echte applicatie zou je de client kunnen laten weten dat de bewerking
is mislukt en dat deze opnieuw moet proberen.
